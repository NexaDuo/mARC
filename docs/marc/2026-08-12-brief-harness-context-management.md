# Research brief: how the three harnesses handle context-window management and automatic compaction

**Produced by:** `@research` · **Issue:** [#181](https://github.com/NexaDuo/mARC/issues/181)
**Materialized by:** `@techlead`, per the durable-artifact policy ([#46](https://github.com/NexaDuo/mARC/issues/46))
**Source comment:** https://github.com/NexaDuo/mARC/issues/181#issuecomment-5268540207
**Date:** 2026-08-12

## Why this was commissioned

mARC retired its own context-size advisory (decision:
[#181](https://github.com/NexaDuo/mARC/issues/181#issuecomment-5268451452)) on the
grounds that the Claude Code harness already owns the problem and measures it
correctly, where mARC's guard only declared the window. Retiring a guard on the
grounds that "the harness handles it" is only sound if the harness actually does —
on every harness mARC ships. This brief establishes that, per harness, from primary
sources.

## The brief, as delivered

> **`@techlead` note, for accuracy:** the brief refers in places to the status-line
> bridge as "deferred in #181". It was in fact **cancelled**, not deferred, by the
> decision recorded the same day. `@research` was dispatched before that wording
> was settled. The finding this affects is a useful one and stands on its own:
> Antigravity's status line carries the same `context_window` schema as Claude
> Code's, so the bridge would be no harder there — should it ever be revived.
> The rest of the brief is reproduced unedited.

**TL;DR** — Claude Code and GitHub Copilot CLI both ship documented, on-by-default automatic compaction with a fixed or configurable trigger point, and both keep live context/token data off the hook surface mARC uses (`PostToolUse`/`postToolUse`) while exposing it only through an opt-in status-line channel. Google Antigravity's CLI (`agy`) is the odd one out: its official docs document *no* compaction mechanism, threshold, or setting at all — no `/compact` command exists in the documented command list, and none of the seven CLI-doc pages I fetched (`overview`, `using`, `reference`, `features`, `best-practices`, `settings`, `plugins`) mentions compaction. The only signal that `agy` compacts context automatically is a user forum complaint, not a primary source, and it's ambiguous whether that describes the CLI or the Antigravity IDE app. `agy`'s status line, however, *does* document the same `context_window` schema as Claude Code's — so if mARC ever revives the status-line-bridge idea (deferred in #181), Antigravity is not worse-positioned than Claude Code for that specific mechanism, even though its own native auto-compaction is unconfirmed. Retiring mARC's context-size advisory is safe for Claude Code (confirmed native replacement) and probably safe for Copilot CLI (confirmed native replacement, non-configurable), but leaves a **documented gap** on Antigravity: there is no confirmed native compaction to lean on, so if `agy` truly has none, a user on Antigravity who was relying on mARC's now-retired advisory has nothing native filling that role.

### Comparison table

| | Claude Code | Google Antigravity (`agy` CLI) | GitHub Copilot CLI |
|---|---|---|---|
| Auto-compaction, default state | **On** (`autoCompactEnabled` default `true`) [measured/doc] | **Not found** in official docs; a forum post reports aggressive automatic compaction but doesn't confirm CLI-vs-IDE surface or default state [reported, low confidence] | **On**, starts at ~80% of window, pauses at ~95% if unfinished [measured/doc] |
| Threshold/window configurable | Yes — `autoCompactWindow` (100k–1M tokens), `/autocompact`, `--autocompact` flag, `CLAUDE_CODE_AUTO_COMPACT_WINDOW` env var; can be disabled via `DISABLE_AUTO_COMPACT` env var [measured/doc] | **Not found** — no compaction key in the documented `settings.json` key list, no `/compact` command in the documented command list | **No** — thresholds are fixed at ~80%/95%; an open feature request (#1761) asks for exactly this and is unresolved [measured/doc + reported] |
| Real context window/usage exposed to hooks/extensions | **No** on the hook surface (no context/token fields in any `PreToolUse`/`PostToolUse`/`PreCompact` input) — confirmed in the prior #181 research thread. **Yes** on the status line (`context_window.*`, `used_percentage`, `current_usage`) | **No** on hooks (agy symlinks Claude Code's hook scripts — inherits the same limitation structurally, though agy's own hook JSON schema wasn't independently verified). **Yes** on the status line: `agy`'s statusline doc lists the identical `context_window` object (`context_window_size`, `used_percentage`, `remaining_percentage`, `current_usage`) [measured/doc] | **No** on any documented hook event (`sessionStart`, `postToolUse`, `preToolUse`, `preCompact`, etc. — none carry context/token fields) [measured/doc]. A `statusLine.command` surface exposing `context_window_size`/`used_percentage`/`remaining_tokens` exists but is explicitly **experimental** and documented only in community blogs/gists, not found on `docs.github.com` [reported] |

| Per-model window tuning documented | Yes — "When unset, Claude Code uses a window tuned for your model"; status line default is `200000` or `1000000` "for models with extended context" [measured/doc] | Not found (the CLI settings/reference pages don't document per-model window sizes) | Documented only qualitatively — "context window has a fixed size... that varies by model," no numbers given [measured/doc] |

### Findings

- **Claude Code auto-compacts by default with a documented, tunable window.** [measured] — code.claude.com/docs/en/settings (fetched). > "autoCompactEnabled — Default: true. Automatically compact the conversation when context approaches the limit." and "autoCompactWindow — How full the context window gets before Claude Code compacts automatically, in tokens from 100000 to 1000000. When unset, Claude Code uses a window tuned for your model." — confirms every fact listed in the dispatch, plus one addition: `DISABLE_AUTO_COMPACT` is the env var to turn autocompact off entirely. https://code.claude.com/docs/en/settings

- **Claude Code emits its own context/auto-compact warning, distinct from spend/usage-limit messages.** [measured] — code.claude.com/docs/en/costs (fetched). > "A context or auto-compact warning: not a usage limit. The conversation has grown close to the session's auto-compact window, the threshold where Claude Code summarizes older history to free space." https://code.claude.com/docs/en/costs

- **Claude Code's status line is the only place the real, live context window reaches user-facing scripting — and it has documented null-state edge cases.** [measured] — code.claude.com/docs/en/statusline (fetched). > "context_window.context_window_size — Maximum context window size in tokens. 200000 by default, or 1000000 for models with extended context." and "context_window.current_usage: null before the first API call in a session, and again after /compact until the next API call repopulates it." This matches and extends the finding already recorded in the prior #181 research thread (hooks get none of this; status line gets all of it). https://code.claude.com/docs/en/statusline

- **GitHub Copilot CLI auto-compacts by default at a fixed, non-configurable percentage of the window.** [measured] — GitHub Docs, "Managing context in GitHub Copilot CLI" (fetched, current). > "When your conversation reaches approximately 80% of the context window's capacity, Copilot CLI automatically starts compacting the context in the background... If the context fills to approximately 95% before compaction finishes, Copilot CLI pauses briefly to wait for compaction to complete." No setting, flag, or env var to change this threshold is documented anywhere on this page. https://docs.github.com/en/copilot/concepts/agents/copilot-cli/context-management

- **The 80%/95% thresholds are explicitly fixed, and a user-filed feature request to make them configurable is open and unresolved.** [measured — GitHub issue] — `github/copilot-cli` issue #1761 (fetched). > "The current fixed threshold of 95% is too late." No maintainer response committing to a fix. https://github.com/github/copilot-cli/issues/1761

- **No Copilot CLI hook event — including the one literally named for this moment — carries context or token data.** [measured] — GitHub Docs, "GitHub Copilot hooks reference" (fetched). The documented event list is `sessionStart`, `sessionEnd`, `userPromptSubmitted`, `preToolUse`, `postToolUse`, `postToolUseFailure`, `agentStop`, `subagentStart`, `subagentStop`, `errorOccurred`, and `preCompact` — none of their input-field lists include context window size, token usage, or context percentage. This directly matches mARC's own hook usage (`sessionStart`, `postToolUse` in `harnesses/copilot/marc/hooks/hooks.json`) — mARC's Copilot hook cannot see the number it would need even in principle. https://docs.github.com/en/copilot/reference/hooks-reference

- **A context-usage status line exists for Copilot CLI, but it is experimental and not found in official docs.** [reported — community blogs/gists, not docs.github.com] — multiple independent write-ups (tgrall.github.io, blog.madkoo.net, gist.github.com/CesarD) describe `statusLine.command` in `~/.copilot/settings.json`, gated behind `copilot --experimental` or a `feature_flags` override, receiving a JSON payload with `context_window_size`, `used_percentage`, `last_call_input_tokens`, and `remaining_tokens`. I could not find this feature documented on any `docs.github.com` page in the sources I fetched (context-management, hooks-reference). Treat as real (multiple independent, consistent, dated write-ups from May 2026) but unofficial/subject to change, per the authors' own caveat: "As of May 1st, 2026, statusLine.command is an experimental feature and is subject to change."

- **Antigravity's CLI (`agy`) command reference documents no `/compact` command and no compaction-related setting.** [measured, negative finding] — antigravity.google/docs/cli/reference (fetched, full slash-command list extracted). 29 commands are documented (`/context`, `/clear`, `/rewind`, `/fork`, `/hooks`, `/statusline`, etc.); none is `/compact` or equivalent. antigravity.google/docs/cli/settings (fetched) lists 15 settings.json keys (`toolPermission`, `artifactReviewPolicy`, `verbosity`, `useG1Credits`, etc.); none concerns compaction or context window. https://antigravity.google/docs/cli/reference , https://antigravity.google/docs/cli/settings

- **Antigravity's `/context` command only visualizes usage; it does not describe automatic compaction behavior.** [measured] — antigravity.google/docs/cli/reference (fetched). > "/context — Open the context usage visualization panel." No accompanying text about what happens automatically when the window fills. https://antigravity.google/docs/cli/reference

- **Antigravity's own status-line docs expose the identical `context_window` schema Claude Code uses**, including `context_window_size`, `used_percentage`, `remaining_percentage`, and a `current_usage` sub-object with per-category token counts. [measured] — antigravity.google/docs/cli/statusline (fetched). This is a genuinely useful finding for mARC beyond the dispatch's question: **if** the deferred status-line bridge (#181, option A) is ever revived, Antigravity is not a harder target than Claude Code for that specific mechanism — its statusLine surface already carries the same live numbers. https://antigravity.google/docs/cli/statusline

- **Antigravity's hooks documentation gives no field-level schema and does not mention context/token data.** [measured, negative finding] — antigravity.google/docs/cli/plugins (fetched). > "Hooks intercept agent actions right before or immediately after execution. They are useful for running automated pre-flight checks or post-generation formats." No JSON schema, no context fields, documented on this page. Combined with the repo fact that `harnesses/antigravity/marc/hooks` is a symlink to Claude Code's hook scripts (`harnesses/claude-code/marc/hooks`), the practical consequence is the same as Claude Code's hook-side gap — but I could not independently confirm that `agy`'s own hook *runtime* passes the identical JSON schema Claude Code's hook runtime does; I'm treating "the symlinked scripts inherit the CC hook-input contract" as **[inference — my own reasoning]**, not a directly confirmed fact, because I did not find an `agy` hook input-schema reference to compare against. https://antigravity.google/docs/cli/plugins

- **The only evidence that `agy` compacts context automatically at all is a user forum thread, and it doesn't cleanly identify which Antigravity surface (IDE app vs. CLI) is being described.** [reported, low confidence] — Google AI Developers Forum, "Frustrated with aggressive context compaction before plan execution," posted 2026-05-30, reply 2026-06-02. > The original poster criticizes "Antigravity" broadly; a reply references both "Gemini CLI" and "Antigravity CLI Architecture." No official Google documentation corroborates automatic compaction, a threshold, or a toggle for `agy` specifically. https://discuss.ai.google.dev/t/frustrated-with-aggressive-context-compaction-before-plan-execution/167983

- **No per-model context-window numbers are documented for Antigravity's CLI.** [not found] — checked `overview`, `using`, `reference`, `features`, `settings`, `best-practices`, `plugins`. None gives token-count figures for any Gemini model inside the `agy` CLI. (A separate, unverifiable community claim exists that a specific model is capped at 128k inside Antigravity, but I did not fetch a primary source for it and am not citing it as a finding.)

### Implications for the decision

- **Claude Code:** the #181 decision's characterization is confirmed and, if anything, understated — Claude Code's own docs recommend using its status line for exactly the purpose mARC's now-retired advisory served ("configure your status line to display it continuously," per code.claude.com/docs/en/costs). Retiring mARC's advisory here trades a guessing mechanism for a measuring one, as already decided. No gap.

- **GitHub Copilot CLI:** retiring the advisory is a comparable trade, though weaker than Claude Code's: compaction is on by default and Copilot's own docs point users at it, but the threshold is fixed (not configurable) and there's an open, unresolved complaint (#1761) that 95% is "too late." The user-facing warning is compaction-starting-at-80% itself, not a separate advisory. mARC's own hook (`postToolUse`) still can't see any of these numbers — same structural gap as Claude Code's hooks, confirmed directly against the current hooks reference, not inferred. Net: retiring is defensible (native mechanism exists, is on by default, and mARC's guard could never have measured it anyway), but Copilot CLI users get a less-tunable native safety net than Claude Code users.

- **Google Antigravity (`agy` CLI):** this is the harness where "the native mechanism already handles it" **cannot be confirmed** from primary sources. The official CLI docs I fetched are silent on compaction entirely — no `/compact` command, no compaction setting, no documented default-on/off state. The only signal of automatic compaction is a forum complaint that doesn't even clearly name the CLI surface. If `agy` genuinely has no native compaction (plausible, given the documentation silence and the forum poster's frustration reads as "it truncates/compacts unpredictably," which is a different complaint than "it manages this well"), then retiring mARC's context-size advisory removes a signal from Antigravity with **no confirmed native replacement** — a real, not merely theoretical, gap. The mitigating fact: mARC's advisory was already fail-closed and silent by default on Antigravity too (per the #181 phase-1 ship), so retiring it changes nothing about what an Antigravity user sees *today* — it forecloses ever restoring the signal via the declared-window escape hatch, on a harness where, unlike Claude Code, there's no confirmed native alternative to defer to.
