**TL;DR** — Every technique found is a variant of two ideas #204 already picked: (1) a shared-tracker field (assignee/status) as the claim token, with staleness handled by convention or a lease+TTL, and (2) filesystem isolation via git worktrees. No GitHub API primitive exists to make `set_status` compare-and-swap — confirmed by introspecting the live GraphQL schema, not just docs. Real production systems that face this shape of problem at *scale* (job queues, Renovate) reach for DB-backed lease/heartbeat protocols, but that machinery is explicitly disproportionate to 1-2 operators on one clone. I did not find a documented case of a team building and then removing a locking layer for this exact problem shape. Net: the external evidence **confirms** #204's documentation-only, board-as-mutex + worktree-isolation recommendation; it also surfaces one concrete refinement worth folding in (stale-claim recovery framed as a lease, since GitHub itself models Copilot coding-agent assignment as assignee-based claim + isolated environment).

## Findings

1. **GitHub's own Copilot coding agent uses assignee-as-claim + isolated environment, with no documented anti-collision for double-assignment.** [reported, high confidence] — "Assigning and completing issues with coding agent in GitHub Copilot," GitHub Blog, 2025-06-06, https://github.blog/ai-and-ml/github-copilot/assigning-and-completing-issues-with-coding-agent-in-github-copilot/. > "You assign Copilot an issue and it plans the work, opens a pull request, writes the code, runs the tests, and then asks for your review." The article documents no technical guardrail preventing two agents (or a human and the agent) from being assigned the same issue simultaneously — it relies on human issue-assignment discipline, same shape as #204's convention. This is GitHub's own product validating "assignee/status field as claim" as sufficient at their scale.

2. **GitHub's GraphQL API has no optimistic-concurrency primitive on issue or Projects v2 mutations — confirmed by live schema introspection, not just docs.** [measured, high confidence] — direct `gh api graphql` introspection against `UpdateIssueInput` and `UpdateProjectV2ItemFieldValueInput` run in this session (2026-08-25) against `docs.github.com/en/graphql`. `UpdateIssueInput` fields: `clientMutationId, id, title, body, assigneeIds, assignees, milestoneId, labelIds, labels, state, stateInput, projectIds, issueTypeId, issueType, issueFieldUpdates, agentAssignment` — no version/etag/expected-value field. `UpdateProjectV2ItemFieldValueInput` fields: `clientMutationId, projectId, itemId, fieldId, value` — same absence. Corroborated by GitHub's REST conditional-request docs: > "Conditional requests for unsafe methods, such as POST, PUT, PATCH, and DELETE are not supported unless otherwise noted in the documentation for a specific endpoint" (docs.github.com, "Best practices for using the REST API"). This is a clean, well-evidenced **negative** for point 2: there is no compare-and-swap to reach for; #204 was right that closing the `set_status` race requires either external locking machinery or accepting last-write-wins.

3. **GitHub's `UpdateIssueInput` schema now carries a native `agentAssignment` input object** (`targetRepositoryId, baseRef, customInstructions, customAgent`), confirming GitHub is actively building first-class multi-agent-on-one-issue plumbing, but as of this check it still routes through the same single `assignees`/`state` fields, not a separate claim/version mechanism. [measured, moderate confidence — schema presence is measured, its design intent is inference] Source: same introspection call, 2026-08-25.

4. **Claude Code's own docs describe git-worktree isolation, including a `git worktree lock` claim mechanism, but explicitly scope it to Claude-created worktrees, not cross-tool coordination.** [reported, high confidence] — "Run parallel sessions with worktrees," Claude Code Docs, code.claude.com/docs/en/worktrees (undated, current as of 2026-08-25 fetch). > "While an agent is running, Claude runs `git worktree lock` on its worktree so that concurrent cleanup cannot remove it. The lock is released when the agent finishes." Also: "A worktree gets its own files and branch, but it shares the repository's `.git` directory... with the main checkout." This directly validates the #202/#204 premise that one `.git` directory safely hosts multiple worktrees, and shows the vendor already uses `git worktree lock` as a claim/mutex primitive — a pattern the mARC convention could reuse for worktree bookkeeping, though it says nothing about board-level coordination.

5. **Renovate (a production bot operating against many real repos) recommends "one instance per repository at a time," enforced by external orchestration (Jenkins locks), not by an internal locking layer.** [reported, moderate confidence — one maintainer answer + one discussion] — GitHub Discussion #14727, answered by maintainer `viceice`, 2022-03-18, https://github.com/renovatebot/renovate/discussions/14727. Renovate requires "you need to make sure renovate doesn't use same work directory (baseDir)" per instance; the questioner's own working pattern is "Jenkins locks to ensure only a single renovate instance works on the same repository simultaneously." Renovate does not build compare-and-swap or leases for this; it pushes single-writer discipline outward to the calling CI system. This is the closest real analogue to mARC's situation (one bot, one repo, external tracker) and it lands on "serialize by convention/external gate," not "build a lock."

6. **A real bug where a caching mistake (not a concurrency race) caused a bot to open duplicate PRs.** [reported, moderate confidence] — renovatebot/renovate issue #34308, 2025-02-19, https://github.com/renovatebot/renovate/issues/34308. > "config.prList is being retained between repositories, causing the existing PRs not to be found." Worth flagging as a *negative* finding for point 4: this is a state-management bug, not a concurrent-agent collision, so it is weak evidence for "concurrent agents colliding" specifically, even though it's the best documented "duplicate work from a real bot" incident I found.

7. **Job-queue systems (Postgres-backed workers, `hindsight`, `hermes-agent` kanban tooling) converge on claim + heartbeat + TTL + stale-reclaim as the standard pattern for N workers pulling from a shared queue.** [reported, moderate confidence — blog + GitHub issues, not a paper] — "The Queue Was a Table," dev.to, 2026 (exact date not confirmed on fetch), https://dev.to/daniel_romitelli_44e77dc6/the-queue-was-a-table-how-i-built-claimunclaim-workers-with-skip-locked-stale-recovery-and-1ojm; NousResearch/hermes-agent issue #21147, https://github.com/NousResearch/hermes-agent/issues/21147 ("default claim TTL is 15 minutes, so any one tool call longer than that loses the claim even if the process is healthy"). This pattern is real and well-documented, but it targets workers at a scale (many concurrent claimers, unattended crash recovery) that doesn't match mARC's 1-2 operators — reporting it as **disproportionate for our scale**, per the brief's own instruction. It also surfaces a real failure mode worth naming for the convention: TTL-based reclaim can misfire on a *slow but alive* worker, which argues for a human-recoverable "stale claim" rule (as #204 proposed) over an automatic TTL reaper.

8. **AI-agent worktree blog posts (non-primary, aggregate pattern) report real collision symptoms when agents share one working tree without worktree isolation: overwritten files, stale reads, and contention on `.git/index.lock`.** [reported, low-to-moderate confidence — SEO/blog content, not incident reports with named companies] — e.g. https://www.mindstudio.ai/blog/git-worktrees-parallel-ai-coding-agents (exact byline/date not independently verified). Treat as corroborating color for "why worktree-per-agent," not as a citable incident.

9. **GitHub Actions' `concurrency` key is an officially documented claim/queue primitive** (group name = lock key; `cancel-in-progress` or implicit queueing = contention policy) — but it operates on *workflow runs*, not on issues/Projects items, so it's an architecture analogue, not a directly reusable primitive for `board.py`. [reported, high confidence] — docs.github.com, "Control the concurrency of workflows and jobs" (fetched via search summary, exact quote not independently re-fetched — flagged as a **partial-confidence citation**, since I did not fetch this page directly, only relied on a search-engine summary of it).

## Implications for the decision

- **Point 1 (claim/lease protocols):** confirms #204's board-as-mutex direction. GitHub's own product (Copilot coding agent) and Renovate both use "assignee/status field claims a work item" with no automated stale-reclaim beyond human/CI discipline, at a scale comparable to or larger than mARC's. No evidence anyone builds heartbeat/TTL machinery at small scale; that only shows up in true job-queue systems with many workers.
- **Point 2 (compare-and-swap on GitHub's API):** answered negatively with primary-source certainty (live schema + REST docs). #204's acceptance of "last-write-wins window, documented" is the only option GitHub's API leaves open short of building an external lock service — which is out of proportion here.
- **Point 3 (shared-working-tree conventions):** confirms git worktrees as the standard, vendor-endorsed technique (Claude Code docs explicitly describe multi-worktree-one-`.git` operation and even a native `git worktree lock`). No evidence found on Antigravity's or Copilot's own docs about worktree conventions specifically (gap, see below) — Copilot's coding agent instead runs in an isolated cloud dev environment/branch, a different mechanism achieving the same isolation goal.
- **Point 4 (failure reports):** weak. The one concrete "duplicate PR" bot bug found (Renovate #34308) was a caching defect, not a concurrency race, so it doesn't directly validate the *shape* of collision #204 worried about. I found no post-mortem of two agents literally racing `set_status`-equivalent tracker writes. This is a genuine evidence gap, not a negative finding — see Coverage & gaps.
- **Point 5 (anti-pattern / removed locking):** no case found of a team building then removing coordination code for this exact problem. The nearest signal is indirect: production job-queue lease/TTL patterns are real but are consistently deployed at worker counts far above 1-2, which is itself evidence that such machinery would be disproportionate here — supports #204's no-code stance by absence of any small-scale counter-example, but this is a weaker form of "confirm" than direct anti-pattern evidence would be.

## Coverage & gaps

- **Searched:** GitHub issue-tracker lock/lease/TTL patterns for multi-agent bots; GitHub GraphQL/REST optimistic-concurrency docs (plus live schema introspection); git-worktree conventions for concurrent AI agents; Claude Code / Copilot / Renovate own documentation; bot-collision incident reports and post-mortems; distributed-lock-removed-as-over-engineering pattern.
- **Read (fetched and quoted from):** 9 sources — GitHub Copilot coding-agent blog post; GitHub REST API best-practices docs; two live GraphQL schema introspection queries (`UpdateIssueInput`, `UpdateProjectV2ItemFieldValueInput`, `AgentAssignmentInput`, `IssueStateUpdateInput`); Claude Code worktrees doc; renovatebot/renovate discussion #14727; renovatebot/renovate issue #34308; NousResearch/hermes-agent issue #21147 (via search summary, not independently fetched in full); one dev.to job-queue post (via search summary).
- **NOT found:**
  - Antigravity's own published guidance (if any) on worktree or workspace-sharing conventions for concurrent agents — I found none; #204 already flagged Antigravity's `Workspace: share` as unstudied, and this pass didn't close that gap.
  - Any GitHub Projects v2 REST/GraphQL field for optimistic locking (confirmed absent, not just unsearched).
  - A named, dated incident where two autonomous agents (not humans) actually raced a shared-tracker write and the postmortem is public.
  - A documented case of a team removing a lock/coordination layer as over-engineering for this exact "N agents, one tracker" shape.
- **Staleness / bias notes:** the Copilot blog post is from June 2025 and may predate later concurrency features; the Renovate discussion is from March 2022 (dated, but the underlying git single-`.git`-dir mechanics it describes haven't changed). Several sources (mindstudio.ai, medium.com posts) are SEO/marketing-adjacent blog content, not incident reports — weighted low and flagged inline. The GitHub Actions `concurrency` key finding (#9) was not independently re-fetched from the primary docs page in this session and rests on a search-engine summary; treat its exact wording as unverified, though the existence of the feature itself is well known and consistent across multiple independent search hits.

## Verdict: CONFIRM

The external evidence **confirms** #204's documentation-only recommendation. No GitHub API primitive exists to make `board.py::set_status` compare-and-swap (verified directly against the live schema, not just docs), so there is no "free" fix available even if the team wanted one. Every real-world analogue at comparable scale — GitHub's own Copilot coding-agent assignment model and Renovate's single-instance-per-repo practice — resolves this exact problem shape (N agents/bots, one tracker, one working copy) with a claim-field-plus-human-discipline convention, not code; the more rigorous claim/lease/heartbeat/TTL machinery that does exist in the wild belongs to job-queue systems built for many concurrent unattended workers, a scale mismatch with mARC's 1-2 operators that would make importing it disproportionate. The one refinement worth folding into the convention write-up, not the recommendation itself, is to explicitly frame the "stale-claim recovery rule" as a lease with a human-checked TTL (per the job-queue prior art's warning that automatic TTL reclaim misfires on slow-but-alive workers) rather than leaving staleness undefined, and to note the git-worktree-per-operator pattern is exactly what Claude Code's own docs already assume is safe on one `.git` directory.
